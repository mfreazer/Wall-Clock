# Release readiness: decisions and verification plan

Status: **planning only; not an approved policy or a test report**. The development implementation and the original requirements are described in [Implementation.md](Implementation.md) and [SyRS.md](SyRS.md). [Traceability.md](Traceability.md) is the current requirement-by-requirement evidence record. Do not treat the checks below as passed or turn unspecified limits into requirements without owner approval.

## 1. Decide the access policy (WC-SYS-058)

The owner intends a **standalone clock on a shared local network**, with both viewing and changes restricted to authorized users, using a browser password and physical USB for initial provisioning and recovery. No physical hardware is currently available. The precise credential lifecycle, transport trust and recovery procedure are not yet decided. The legacy listener is temporarily disabled; the intended protected browser interface is not implemented yet.

The unauthenticated HTTP listener is now **temporarily disabled**: the firmware registers the old handlers but does not start or poll the server. Browser configuration is therefore unavailable while HTTPS and password access are developed. The host suite checks that the legacy listener is not started or polled, including after Wi-Fi provisioning and reboot; this is not a physical-network test. The legacy handlers remain unauthenticated and must not be re-enabled on a shared network. JSON-only POSTs, `If-Match`, and lack of CORS are not authentication; they do not prevent DNS rebinding. The serial interface can change Wi-Fi credentials, and credentials in NVS are not encrypted by this example.

The owner should choose and record the intended network and who may read or change settings. Possible directions, **not approved designs**, include:

| Direction | What must be decided and verified |
| --- | --- |
| Isolated trusted network | Whether every device and user on that network is trusted, how isolation is maintained and tested, who has physical/serial access, and whether the remaining browser-origin and availability risks are acceptable. Network isolation does not by itself remove DNS rebinding. |
| Shared local network with restricted configuration | Who is authorized, how credentials are provisioned, stored, rotated and recovered, whether reads also require authorization, and how transport confidentiality, browser-origin/DNS-rebinding defenses, denial of service, and serial access are handled. Adding a password over plain HTTP alone is not sufficient. |
| Another arrangement | Define the trust boundary, authorized clients and administrators, network exposure, threat assumptions, provisioning/recovery, and acceptable residual risks before selecting controls. |

### Baseline and next design choices

`scenario_config_api` in [the host firmware harness](../test/host/firmware_harness.cpp) directly invokes the dormant handlers, gets the configuration and its ETag, and successfully changes settings without credentials. The harness bypasses the network listener; this is evidence of handler behavior, not a physical-network or browser exploit test. The existing positive test is functional coverage, not a security requirement; it must be adapted when access controls are implemented. No authentication, DNS-rebinding mitigation or early body limit has been demonstrated.

Run `./tools/sandbox_security_gate.sh` for a focused host check of the selected access policy. **It currently fails (5/5 checks)** because unauthenticated reads and writes are accepted. It tests denial of status/settings reads, denial of a valid write even with the current ETag, and no resulting RAM or simulated NVS change. A mutation that returned 403 after applying the write was still rejected by the state checks. This intentionally failing security gate is separate from the existing host suite until authorization is implemented; passing it alone would not verify TLS, authorized use, DNS rebinding, real networking, or physical security.

The owner has selected password-based browser access and physical USB setup/recovery. Still open: how a browser establishes and verifies the device's identity, how the password is provisioned and reset over USB, and what physical access is trusted. Credentials need confidentiality and server identity protection in transit, and browser-origin/DNS-rebinding defenses must be designed and tested rather than assumed. Passwords and private keys must not be hard-coded, printed in logs or committed.

A **not-yet-integrated** password-verification and HTTP Basic helper is under [`security/`](../security/). It uses the Mbed TLS PBKDF2-HMAC-SHA256 and constant-time comparison APIs, limits input lengths, and requires an explicit iteration range. It does not generate a salt, provide TLS, implement the intended protected web server, or decide a production iteration cost. `./tools/sandbox_password_verifier_test.sh` runs host known-answer and malformed-header checks; `./tools/sandbox_esp32_password_test.sh RETAINED_BUILD` runs a small target probe after `./tools/sandbox_esp32_build.sh --emulate --keep`. The target probe uses only two iterations to test correctness, not security strength. Hardware timing and secure random salt generation remain to be verified; the legacy HTTP handlers remain unauthenticated and their listener is disabled.

**Implementation investigation, not a selection:** the pinned Arduino ESP32 2.0.17 upstream tree contains `esp_https_server.h` and `libesp_https_server.a`. A separate [probe](../test/security/https_link_probe.cpp) compiled and linked in the sandbox with the third-party test compiler; its Xtensa ELF contains `httpd_ssl_start` and `httpd_ssl_stop`. Removing those calls made the symbol check fail. A second mode inserted the probe into a scratch copy of the clock and also linked: the platform reported 46,380 bytes static RAM and 979,589 bytes flash, versus 45,768 and 845,545 for the unchanged clock in the same bundle. These are build-time figures only, not TLS handshake heap or an estimate of a completed implementation.

To reproduce, run `./tools/sandbox_esp32_build.sh --keep`, then `./tools/sandbox_esp32_https_link_test.sh RETAINED_BUILD` for the standalone probe or add `--with-clock` for the scratch-copy build. The runner checks selected tool hashes and versions and isolates compilation; it does not authenticate the bundle or compiler. Neither probe has a certificate or authentication, establishes a TLS connection, or replaces the clock's HTTP interface. Neither is a runtime/network/target test or a security claim. **Never flash or deploy either probe.** Evaluate package provenance, TLS identity, server integration, resource consumption and denial-of-service behavior before selecting a design.

### Candidate design for review — not approved or implemented

A private local certificate authority is a possible fit for a standalone device without a public domain: a trusted setup computer signs a per-device certificate, the clock receives only its own certificate and private key over USB, and each authorized browser device is configured to trust the private CA. Clients must use the certificate's matching stable device name or IP, and must reject certificate errors rather than clicking through warnings. This requires deliberate trust installation on every client and a plan for naming, key protection, renewal, revocation and replacement; some client platforms make trust installation difficult. The CA private key must remain off the clock and be protected. Alternatively, a publicly trusted certificate requires an appropriate domain and a practical issuance/renewal process. **The owner has not chosen a trust model**, so neither is a requirement yet.

Subject to that decision and a detailed threat model, a possible architecture is: no cleartext configuration endpoint or HTTP fallback; fail closed until identity and access credentials are provisioned; a well-reviewed password verifier and secure session mechanism; authorization on all protected routes; browser-origin/CSRF and DNS-rebinding protections; bounded requests, connection/login attempts and storage writes; and explicit USB-only credential recovery. Password handling, cookie/session attributes, session expiration, limits and recovery behavior must be specified and reviewed, not inferred from this sketch. NVS encryption and protection from physical extraction depend on the eventual board/security configuration and are not established here. No implementation should treat an ETag as authorization or log secrets.

For any chosen design, specify behavior for unauthorized requests, first setup and recovery, credential loss, browser access, and network changes. Implement and test against those decisions, including negative tests for unauthorized and browser-origin requests. Early request-size handling and write endurance/rate controls also need explicit design; the current application body check occurs after WebServer buffering. Do not publish credentials, network identifiers, or private device data in test records.

## 2. Establish a verified build for physical testing

The Git-stored snapshot and sandbox fallback are **emulator-only; never flash or release them**. The fallback compiler comes from a pinned third-party mirror, and its official provenance is unverified. A successful standard PlatformIO CI job is useful supplemental build evidence, but is not a checksum verification of that mirror or a hardware test. See [Sandbox-ESP32.md](Sandbox-ESP32.md).

Before producing a physical-test image:

1. Identify the exact source commit, board and build configuration, and use a trusted build environment with verified PlatformIO/toolchain/framework packages and dependency identities. Record the verification method and trusted source of checksums or signatures; a self-reported checksum alone establishes identity, not authenticity.
2. Run the required host suite and a target build from that source. Record tool and dependency versions, commands, results and hashes of the produced files. Preserve build logs without credentials or unrelated private information.
3. Record the precise binary and flash layout used on the board and link them to the evidence. A successful build is not evidence of correct physical behavior. If package provenance cannot be established, mark the build blocked rather than relabeling the emulator image.

## 3. Prepare hardware acceptance (WC-SYS-057, 060–064, 070–072)

**Prerequisites, not yet supplied or approved:** exact ESP32 board/revision; LED model, count and wiring; supply and protection ratings; level shifting and grounding; controls; test network; reference clock and measurement equipment; intended operating conditions. Agree on geometry, interaction, outage/restart behavior, accuracy, latency, and brightness/current interpretations and limits in the SyRS before declaring acceptance. The development defaults are not approvals.

Review the electrical guidance in [Implementation.md](Implementation.md) with the actual component datasheets and installation. The firmware brightness setting is **not a current limiter**. Do not power the strip through the ESP32 board. Disconnect power before wiring; use a suitably rated supply, wiring, protection, and instrumentation. Do not conduct destructive or interrupted-write experiments on production hardware or with irreplaceable data.

Once prerequisites and criteria are approved, use a verified physical-test build and record the build identity, fixture, setup, procedure, expected result, measured result, and pass/fail or blocked status for each run:

- **Power and display:** inspect wiring against the approved design; measure supply voltage, current and relevant temperatures under approved worst-case display configurations and operating conditions. Verify index orientation, colors, mapping, collisions, brightness behavior and update timing against approved criteria. Record instrument and uncertainty; software allocation status does not prove the strip works.
- **Persistence and recovery:** save a non-sensitive configuration, perform a controlled restart and power cycle, and compare settings and display behavior. Separately test storage failures and interruptions at defined write stages using an appropriate test fixture; define acceptable recovery and data-loss behavior first. Completed writes in the emulator do not prove physical power-loss safety.
- **Network, time and UI:** on the approved test network, verify serial provisioning, connection and SNTP acquisition, status and display; exercise the actual browser/API, validation, and concurrent changes. Test network/time-service loss, reconnect and cold restart against the approved policy. Compare time against a traceable reference over the agreed interval, including holdover; a sync callback alone does not establish accuracy.
- **Controls and timing:** test the actual button and GPIO/LED signal with suitable instruments, including debounce, output timing and update latency under representative load. Check time-zone behavior against the approved rule and independent expected values, including relevant transitions.
- **Security:** test the approved access policy from authorized and unauthorized clients and browser contexts, including the documented DNS-rebinding risk, provisioning/recovery and request/resource limits. Do not infer security from a successful functional browser test.

Any unavailable equipment, unspecified criterion or unrun case stays **blocked/not run**, not passed. Update [Traceability.md](Traceability.md) with links to actual results; neither host stubs nor emulator runs substitute for physical acceptance.
